# PATANYX blocklist allowlist -- hosts that must never reach the shipped list.
#
# WHY THIS EXISTS. Upstream feeds report popular, legitimate services from time
# to time, usually because phishing was once hosted on one. A listed host also
# covers its subdomains, so importing such a report unchanged would take a whole
# service with it. This file is where those reports are refused.
#
# The failure mode is silent, which is why the refusal has to be deliberate: a
# blocklist has no way to report what it blocked in error. The user simply sees
# a site that does not work, and PATANYX ships no appeal path.
#
# The existing guard, PROTECTED_SUFFIXES in hostrules.rs, is a different tool
# for a different failure: it catches a feed listing a bare PLATFORM suffix
# (`github.io`), where the accident is structural and the blast radius is a
# hosting provider. It is twenty-eight hand-picked entries and was never meant
# to know that `yotpo.com` is a real business. This file covers the other case:
# a popular, legitimate site that a feed reported because phishing was hosted
# on it once.
#
# WHAT AN ENTRY MEANS. "This exact host does not belong on a PHISHING
# blocklist." That is narrower than "this host is safe, or reputable, or
# pleasant", and the difference is load-bearing. PATANYX blocks hosts REPORTED
# AS PHISHING and says exactly that on the banner; it is not a content filter,
# a gambling filter or a reputation service. A host can be adult, ad-choked,
# high-risk or simply unpleasant and still not be phishing, and blocking it here
# tells the user something untrue about it. Removing such a host is a
# correction, not an endorsement.
#
# It removes the host from the merged list; it does NOT remove subdomains. That asymmetry
# is deliberate and it is the whole reason exact-match is safe here:
# `gravatar.com` stops being blocked while a feed entry for
# `phish.gravatar.com` goes on being blocked, because the subdomain is a claim
# about a specific attacker page rather than about the service.
#
# ADDING AN ENTRY IS A DECISION TO STOP PROTECTING SOMETHING. Every line needs
# a reason and a source, because the failure mode of a careless allowlist is
# silent and unbounded: an attacker who gets a domain in here buys permanent
# immunity across every install. Rank figures are Tranco top-1M positions on
# the date given. Prefer removing the reason for the listing (report the false
# positive upstream) over carrying an entry here forever.
#
# Format: one host per line. Blank lines and lines beginning with # ignored.

# THE TIE-BREAK IS ASYMMETRY OF HARM, and it decides every ambiguous case here.

# the per-tab override. A wrong allow is silent and permanent -- no banner, no
# signal, protection quietly absent on every install. So an entry needs
# positive evidence that a host is legitimate; "not obviously malicious" is not
# enough, and popularity is not evidence.
